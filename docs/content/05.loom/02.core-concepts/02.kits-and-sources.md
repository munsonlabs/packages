A kit is everything your app lets widgets use: its data and actions, its blocks, its themes, and the guard every action passes through.

```js
const kit = createKit({ id, sources, blocks, themes, describe, guard })
```

| Option     | Is                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `id`       | Names the kit. A published [library](/loom/core-concepts/libraries) records it, so a loader can tell one made for another kit. |
| `sources`  | What definitions can bind to.                                                                                                  |
| `blocks`   | Blocks beyond the sixteen built-ins, like [`videoBlock` and `iconBlock`](/loom/core-concepts/blocks).                          |
| `describe` | A short label for a piece of data, for sample pickers and logs.                                                                |
| `themes`   | Token values widgets start from; the first is the default. See [Tokens and themes](/loom/core-concepts/tokens-and-themes).     |
| `guard`    | Sees every action before it runs, and can stop it. See [Guarding actions](#guarding-actions).                                  |

Kits are values, not global registries: two apps (or a timeline and a shop) can each have their own on one page.

## Data and context

Every widget renders one piece of **data**: whatever your sources read. **Context** is whatever they need from the app: a native bridge, a cart, a router. Pass both to `<Widget>`, or provide them once:

```js
provideKit(kit, context)
```

## Sources

```js
defineSource({
  id: 'event',
  label: 'Event',
  description: "An event's date and calendar actions.",
  fields: {
    date: { type: 'string', description: 'Start date, localised' },
    hasCorrectDates: { type: 'boolean' },
    addToCalendar: { type: 'action' },
  },
  setup: ({ data, context }) => useEvent(data, context),
})
```

- **`fields`** declare what the source returns, typed `string`, `number`, `boolean`, `list`, `object` or `action`. Editors offer them; the validator checks against them.
- **`setup`** runs once per rendered widget, the first time a binding reaches the source, inside the widget's effect scope. Return refs, computeds and functions: loom unwraps refs as it reads.
- **`data` and `index` are read-only refs**, so destructure freely and pass them on: composables that take a ref or a getter read them with `toValue`, and stay reactive when the widget's data changes.
- **`context` is a plain value**, read when the source sets up. Keep what changes reactive inside it (a reactive cart, a bridge), rather than swapping the context itself.
- **`primary: true`** lists a source first in the studio. Use it for the data's own fields.

`setup` is where your composables plug in unchanged. Shape the arguments they expect, call them, return the result. One that takes props rather than refs gets getters over them:

```js
setup: ({ data, index, context }) =>
  useEvent(
    {
      get story() {
        return data.value
      },
      get index() {
        return index.value
      },
    },
    context,
  ),
```

## Lists

A `list` field can describe its items, so a `Repeat` bound to it offers their fields as `item.*`:

```js
children: { type: 'list', item: { '': 'object', 'entry.title': 'string', read: 'boolean' } }
```

`''` is the item itself, for passing it to an action: `{ "action": "openArticle.openArticle", "arg": "item" }`.

## Guarding actions

A kit can see every action before any widget runs it, and stop it. That's where a paywall goes: once, in the kit, rather than in every widget, variant or composable.

```js
createKit({
  // …
  guard: ({ action, arg, data: story, index, context: bridge }) => {
    if (!story.locked || action === 'actions.share') return true // let it run
    bridge.call('showPaywall', story, index) // do this instead
    return false
  },
})
```

The guard gets the bound path (`actions.open`), its resolved argument (a `Repeat`'s `item`, say), the clicked node's id, and the widget's data, index and context. Return `false` to stop the action, anything else to let it run. It may return a promise; the action runs once it resolves to anything but `false`. A stopped link doesn't navigate.

Widgets don't need a variant for it: a locked story's card works like any other, and tapping it runs the guard. Add a variant only when a locked card should look different.

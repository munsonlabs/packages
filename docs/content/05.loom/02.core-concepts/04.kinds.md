A kind is a sort of data your widgets are made for, an article, an event, a product, and where a new widget of that kind starts.

```js
defineKind({
  id: 'event',
  label: 'Event',
  icon: 'i-lucide-calendar',
  matches: (story) => story.entry.type === 'event',
  sources: ['event'], // listed first in the studio
  starter: () => eventCard, // without its id, name and kind
})
```

Each definition records the kind it's for: `"kind": "event"`.

## Picking a widget for the data

```vue
<Widget :kit="kit" :definitions="published" :data="story">
  <template #fallback="{ data }">Nothing for this one</template>
</Widget>
```

With `definitions`, the widget uses the definition whose kind `matches` the data most specifically (see [Narrowing a kind](#narrowing-a-kind)); among equally specific ones, the first. When none does, the `fallback` slot renders, or nothing. The same lookup is `matchDefinition(kit, data, definitions)`.

| Different…                    | Use                                       |
| ----------------------------- | ----------------------------------------- |
| data shape or actions         | a kind                                    |
| presentation of the same data | a [variant](/loom/core-concepts/variants) |

## Narrowing a kind

A kind can `extends` one listed before it. Data must match the base and the kind's own `matches`, and the base's `sources`, `starter` and `icon` stand in for any it leaves out:

```js
defineKind({
  id: 'breaking',
  label: 'Breaking',
  extends: 'article',
  matches: (story) => story.entry.tags?.includes('breaking'),
})
```

Deeper kinds are more specific, and the most specific match wins, wherever its widget sits in the list. So a breaking story gets the breaking widget, and every other article the article one.

## Kinds made in an editor

A kind can also be JSON, so Loom Studio can make one and a [library](/loom/core-concepts/libraries) can carry it. Instead of a `matches` function it lists conditions on the raw data, all of which must hold:

```json
{
  "id": "breaking",
  "label": "Breaking",
  "extends": "article",
  "where": [{ "path": "entry.tags", "op": "includes", "value": "breaking" }],
  "sources": ["time", "labels"],
  "starter": { "root": { "id": "root", "type": "Stack", "children": [] } }
}
```

| `op`       | Holds when the value at `path`…        |
| ---------- | -------------------------------------- |
| `equals`   | is `value`                             |
| `in`       | is one of the list `value`             |
| `includes` | is a list or string containing `value` |
| `exists`   | is anything but `null` or `undefined`  |

Prefix a path with `!` to negate its condition. A kind that extends nothing needs at least one condition and a `starter`.

Conditions read the data itself, not sources: kinds are picked before a widget, and so its sources, exist. A test that needs a source's value (is it live now?) belongs in a kind written in code, or a [variant](/loom/core-concepts/variants) rule.

`withKinds(kit, specs)` returns the kit with them added, each extending a kit kind or one before it; it throws on one with errors. `validateKind(kit, spec)` lists those errors first. `loadLibrary` does both for a library's kinds, and skips the ones that don't fit.

## Starting a widget

```js
createDefinition(kit, 'event', { id: 'gig', name: 'Gig' })
```

copies the kind's starter with the identity given. Loom Studio's `<NewWidgetModal>` does this from a picker of the kit's kinds.

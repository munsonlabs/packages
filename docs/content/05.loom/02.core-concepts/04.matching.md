Each widget says which data it's for, and which of the kit's sources it uses. Both are JSON on the definition, so the studio edits them and a [library](/loom/core-concepts/libraries) carries them.

```json
{
  "version": 2,
  "id": "event-card",
  "name": "Event card",
  "match": [{ "path": "entry.type", "op": "equals", "value": "event" }],
  "uses": ["story", "event", "actions"],
  "root": { "id": "card", "type": "Stack", "children": [] }
}
```

## Conditions

`match` is a list of conditions on the raw data, all of which must hold. A widget with none takes any data.

| `op`       | Holds when the value at `path`…        |
| ---------- | -------------------------------------- |
| `equals`   | is `value`                             |
| `in`       | is one of the list `value`             |
| `includes` | is a list or string containing `value` |
| `exists`   | is anything but `null` or `undefined`  |

`path` is dotted (`entry.tags`). Prefix it with `!` to negate the condition.

Conditions read the data itself, not sources: a widget is picked before it renders, and so before its sources exist. A test that needs a source's value (is it live now?) belongs in a [variant](/loom/core-concepts/variants) rule.

## Picking a widget for the data

```vue
<Widget :kit="kit" :definitions="published" :data="story">
  <template #fallback="{ data }">Nothing for this one</template>
</Widget>
```

With `definitions`, the widget renders the first definition whose conditions the data meets. When none does, the `fallback` slot renders, or nothing. The same lookup is `matchDefinition(data, definitions)`.

Order is the only tie-break, so put narrower widgets first: a breaking-news card (`entry.type` is `article` and `entry.tags` contains `breaking`) before the article card (`entry.type` is `article`). A widget after one whose conditions are all among its own can never be picked; `shadowedWidgets(definitions)` (from `@munsonlabs/loom/editor`) lists them, and the studio warns about them.

| Different…                    | Use                                       |
| ----------------------------- | ----------------------------------------- |
| data, layout or sources       | another widget, with its own conditions   |
| presentation of the same data | a [variant](/loom/core-concepts/variants) |

## What a widget uses

`uses` lists the sources a widget binds to. Editors offer only those, and binding to any other is an error, the same as binding to a source the kit doesn't have, so a widget states up front what it needs from the app. Without `uses`, every source in the kit is in scope.

## Starting a widget

Loom Studio's `<NewWidgetModal>` starts one blank, or as a copy of one in the library, with its conditions and sources to fill in. A copy keeps its source's conditions, so change them, or it'll never be picked after the original.

Every block reads its look from CSS custom properties, all prefixed `--w-`. They come in two tiers.

| Tier      | Tokens                                                                                                                                                                                                                                                             | Set by             |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------ |
| **Scale** | Colours (`bg`, `surface`, `text`, `muted`, `accent`, `accent-contrast`, `border`, `alert`, `success`), the type scale (`text-xs` … `text-2xl`, two weights, two fonts), the space scale (`space-0` … `space-8`), radii (`radius-none` … `radius-full`) and shadows | Mostly themes      |
| **Roles** | What a value is for: `gap`, `padding`, `radius`, `shadow`, `title-size`, `subtitle-size`, `body-size`, `caption-size`, `title-weight`, `title-font`, `link`, `image-radius`, `image-bg`, `button-radius`, `button-padding`                                         | Widgets and themes |

Roles point at the scales by default (`--w-gap: var(--w-space-2)`), and blocks only read roles and colours. So a theme can retune the whole space scale, and a widget can say "my gap is `space-3`" without either knowing the other's numbers.

The full list, with defaults, is `tokens` from `@munsonlabs/loom`.

## Layers

From least to most specific, all on the widget's root:

1. **Defaults**: `styles.css` declares every token at zero specificity.
2. **The theme**: the kit's first theme, or the one `<Widget theme="…">` names.
3. **The definition's `vars`**: this widget's overrides.
4. **The variant's `vars`**: overrides while that variant renders.

```json
{ "vars": { "--w-gap": "var(--w-space-3)", "--w-radius": "var(--w-radius-md)" } }
```

Keep colours in themes and out of definitions where you can: a widget that hardcodes `--w-bg: #fff` won't follow a dark theme. Override a colour in a definition when the widget really is that colour in every theme, like a video tile that's always dark.

## Themes

```js
import { createKit, defineTheme, darkTheme } from '@munsonlabs/loom'

const brand = defineTheme({
  id: 'brand',
  label: 'Brand',
  values: { bg: '#ffffff', accent: '#4f46e5', radius: 'var(--w-radius-lg)', padding: 'var(--w-space-3)' },
})

const brandDark = defineTheme({ id: 'brand-dark', label: 'Brand dark', values: { ...darkTheme.values, ...brand.values, bg: '#18181b' } })

createKit({ themes: [brand, brandDark], ... })
```

```vue
<Widget :definition="card" :data="item" theme="brand-dark" />
```

Keys are token names (`accent`) or full properties (`--w-accent`). Values are any CSS. `lightTheme` (the defaults) and `darkTheme` are built in.

## Light and dark

Pair a light theme with its dark one, and widgets switch between them:

```js
const brand = defineTheme({ id: 'brand', label: 'Brand', dark: 'brand-dark', values: { … } })
const brandDark = defineTheme({ id: 'brand-dark', label: 'Brand dark', values: { … } })
```

```vue
<Widget scheme="auto" … />
<!-- the default: follows the device, live -->
<Widget scheme="dark" … />
<!-- forced, e.g. from the host app's own setting -->
```

Only the light theme names its partner; the dark one is found from it. `theme` names the family, `scheme` picks its light or dark member. A named theme with no counterpart stays as it is; with no theme named, the kit's first theme of the scheme is used. The root carries `data-scheme`. `lightTheme` and `darkTheme` are built in, and already paired.

Every widget sets `color-scheme` on its root, so any value can carry both halves with CSS's own `light-dark()`: `--w-bg: light-dark(#ffffff, #18181b)`, or a style's `border-color: light-dark(#e4e4e7, #3f3f46)`. That's the way to give one widget its own dark colours. It's per value, so it combines with variants (a compact card in dark mode gets both), and `parseLightDark` / `lightDark` read and write it.

Colour is otherwise the theme's job, so a widget that sets `--w-bg`, `--w-surface`, `--w-text`, `--w-muted`, `--w-border` or `--w-accent-contrast` to a single value won't change in dark mode. When the kit has a dark theme, `validateDefinition` warns about it (`severity: 'warning'`; it still renders). Give it a dark value with `light-dark()`, or, if it's deliberate (a video tile that's dark everywhere), set `"fixedColors": true` on the definition. Keep `when: { scheme: 'dark' }` variants for the rare widget whose structure changes in the dark, not just its colours.

## Mapping a host's design system

Theme values can read the host page's own variables, with loom's value as the fallback. The timeline preset picks up a Bolt publisher's theme this way:

```js
defineTheme({
  id: 'timeline',
  label: 'Timeline',
  values: {
    accent: 'var(--timeline-style-accent, #c2410c)',
    font: 'var(--timeline-style-font, system-ui, sans-serif)',
  },
})
```

## Tokens in blocks and editors

A block prop can name the scale its value comes from, and editors then offer that scale instead of free text:

```js
gap: { type: 'string', label: 'Gap', default: 'var(--w-gap)', tokenScale: 'space' }
```

Scales are `color`, `space`, `radius`, `text`, `shadow`, `font` and `weight`. `scaleTokens('space')` lists a scale's steps; `scaleForRole` says which scale each role picks from.
